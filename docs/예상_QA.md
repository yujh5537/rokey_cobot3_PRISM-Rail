# 예상 Q&A — 관제 코어 (심사·질의 대비)

답변은 30초 내 구술 기준. ★ = 나올 확률 높음.

## 알고리즘 선택

**★Q1. 왜 A*나 MAPF(다중 에이전트 경로 탐색)를 안 썼나?**
> 이 토폴로지는 트리형이라 출발-도착 쌍마다 경로가 사실상 유일합니다. 탐색할 공간이 없는데 탐색 알고리즘을 쓰는 건 비용만 내는 선택입니다. 그래서 경로는 정적 테이블로 두고, 엔지니어링 역량을 진짜 문제인 '교통 제어와 선점'에 집중했습니다. 레일이 메시형으로 증설되면 계층 구조상 경로 계층만 탐색형으로 교체하면 됩니다.

**★Q2. 15초 양보 창(yield window)은 어떻게 정했나?**
> 캡슐 최고속 2.0m/s에서 15초는 약 30m — 가장 긴 회랑을 비우고 대피 레인에 들어가기 충분한 거리입니다. 더 짧으면 대피가 늦고, 더 길면 전 경로 잠금에 수렴해 하위 오더가 과잉 지연됩니다. 실제로 전 경로 잠금 방식을 먼저 구현했다가 P1이 2배 지연되는 걸 실측하고 ETA 이동 파도로 교체했습니다.

**Q3. 은행원 알고리즘 같은 교착 회피 기법과 비교하면?**
> 은행원 알고리즘은 자원 요청 그래프 전체를 매번 검사해야 합니다. 우리는 구조적으로 더 싼 해법을 썼습니다 — 회랑 방향 토큰이 양방향 구간의 정면 교착을 규칙 차원에서 제거하고, 진출 예약이 블록 단위 교착을 막습니다. 남는 위험(폭주 시 루프 경계 대치)은 모드 B의 대피 기동이 풀고, 모드 A에서는 감지·통보합니다.

## 검증·신뢰성

**★Q4. 이 수치(67.1초 등)를 어떻게 믿나?**
> 세 겹으로 고정했습니다. ① 회귀 테스트가 기준값 ±0.2초 이탈 시 실패합니다. ② 순수 Python 시뮬 값이 실제 ROS2 경로에서 그대로 재현됨을 확인했습니다(SIM_DONE 85.77 일치). ③ 결정론 테스트 — 몇 번을 돌려도 같은 값입니다. 발표 수치는 전부 명세서 §6-2 표에서 나옵니다. 그 표와 테스트 기준값은 별도 파일이지만, `tools/kpi_report.py` 가 둘을 대조해 어긋나면 exit code 1 로 실패하므로 한쪽만 고쳐진 채로 남을 수 없습니다. ④ 명세서 §3 블록 표는 아예 코드에서 **자동 생성**합니다 — 실제로 수기 동기화 시절에 표와 코드가 8칸 어긋난 적이 있어서, 같은 도구가 재생성 결과와 diff 0 인지까지 검사하도록 바꿨습니다.

**★Q5. 충돌이 안 난다는 보장은?**
> 매 틱 30개 블록 전수에 대해 용량 초과·정면 대치·역주행·추월·구간 이탈 5종 불변식을 검사하는 테스트가 있고, 시연·폭주 전 시나리오에서 위반 0건입니다. 중요한 건 이 안전망(R8)이 모드 A/B 공통이라는 점입니다 — 선점을 꺼도 안전은 안 꺼집니다.

**Q6. 모드 A가 교착에 빠지는 건 시스템 결함 아닌가?**
> 의도된 비교군입니다. 모드 A는 '선점 없는 선착순'이라는 베이스라인이고, 그 한계(폭주 시 그리드락)가 바로 선점 관제가 필요한 이유입니다. 다만 방치하지 않고 관제가 20초 무진행을 감지해 대치 당사자 명단과 함께 DEADLOCK 이벤트를 발행합니다 — 실제 병원이라면 운영자 개입 알람에 해당합니다.

## 설계·도메인

**★Q7. P2, P3가 느려지는 건 문제 아닌가?**
> 트리아지(중증도 분류)와 같은 원리입니다. 항암제 24초 지연과 대량수혈 혈액 4.1초 단축 중 무엇이 환자 안전에 중요한가의 문제입니다. 우리는 그 트레이드오프를 숨기지 않고 대시보드에 '지연 비용'으로 표시하고(장면 ④), 더 나아가 **관제가 스스로 만회합니다** — 양보한 항암제는 슬랙이 3.8초까지 줄자 가속 지령을 받아 마감 78초에 1.40초 여유로 정시 도착합니다. 회복을 끄면 79.27초로 1.27초 지각하는 것을 대조군으로 실측했습니다. 그리고 지연에도 상한이 있습니다 — 파도가 지나가면 롤링 해제로 즉시 복구됩니다(R7).

**Q8. 왜 Code Red가 아니라 Code Crimson인가?**
> 병원 표준 비상 코드에서 Red는 화재입니다. 대량수혈 프로토콜에 화재 코드를 쓰면 실제 운영에서 혼동 사고가 됩니다. 도메인 조사 후 v3.0에서 개칭했습니다.

**Q9. 캡슐이 고장 나면?**
> 현 범위 밖이지만 구조는 준비돼 있습니다 — 고장 캡슐을 EVACUATED 고정 상태로 두면 폐색 규칙이 자동으로 그 블록을 우회 불가 자원으로 처리하고, DEADLOCK 감지가 후속 정체를 통보합니다. 완전한 고장 대응(회수 오더 자동 생성)은 향후 과제로 기술 문서에 명시했습니다.

**Q10. 실제 병원 규모(수백 블록)로 확장되나?**
> 병목은 선점 파도 계산인데 블록 수에 선형이고, 30Hz 틱당 계산량이 현재 수 밀리초 미만입니다. 수백 블록도 여유가 있습니다. 진짜 확장 이슈는 경로 유일성 가정이 깨지는 것이고, 이는 Q1의 계층 교체로 대응합니다.

## 구현·협업

**Q11. ROS 없이 어떻게 관제 로직을 개발·검증했나?**
> 포트-어댑터 분리입니다. 판단 로직 전부를 rclpy 무관 계층(`engine.py`·`bridge.py`)에 두고 노드는 dict→JSON 변환만 합니다. 덕분에 ROS 없이 24종 테스트로 검증한 뒤 실기 통합은 하루 만에 끝났고, 통합 장애 시 '브리지 테스트 통과 여부'로 관제/연동 책임을 즉시 분리할 수 있었습니다.

**Q12. 인터페이스 충돌(관제 vs 연동)이 있었다던데?**
> 같은 날 두 팀이 서로 다른 스키마를 동결한 사고가 실제로 있었습니다. '위치의 진실 소스는 관제 코어, 좌표 변환은 한 곳, 정본은 interface_schema.json 하나'로 합의해 하루 만에 수렴했고, JSON→msg 매핑표로 이행 비용을 최소화했습니다. 협업에서 배운 것: 동결 선언은 반드시 채널 공지와 함께.

## 속도·RTA 회복 (v3.3 신규)

**★Q13. RTA 회복 제어는 어떻게 동작하나?**
> 철도의 여유시분 지연 회복, 항공 AMAN의 RTA 속도 권고와 같은 원리입니다. 매 틱 슬랙 = due − (현재시각 + 샤프트 고정시간 + 수평잔여/평시속도)를 계산해, 임계 10초 아래로 떨어지면 필요 속도를 역산해 지령합니다. 실제 시연에서는 t=44.6초에 슬랙 3.8초에서 걸려 1.05m/s로 첫 지령이 나갑니다(`RTA_ENGAGED` 이벤트). 구현하면서 두 번 틀렸습니다 — ① 샤프트(0.5m/s 고정)는 아무리 가속해도 시간이 줄지 않는 구간이라 **구간을 분해**해 수평 구간만으로 필요 속도를 내야 과소 지령을 막고, ② 매 틱 비례식으로 다시 계산하면 '딱 맞춰 도착'으로 수렴해 여유가 0이 되므로 **지령을 래치(단조 비감소)** 해야 합니다. 최대 속도로도 불가능하면 P2→P1 자동 승격(R12)으로 전환합니다.

**Q14. P1이 두 모드에서 동률(37.6초)인 이유는? P3는 왜 회복이 없나?**
> 화물 운영 정의를 속도에 그대로 매핑했기 때문입니다 — P0 '즉시'와 P1 '최대한 빨리'는 상시 최고속(2.0m/s), P2 '정해진 시간 내'는 평시 1.0 + 필요 시 회복, P3 '완수'는 오염물 안전 저속 0.7 고정입니다. P1은 양 모드 모두 최고속인데 이 시나리오에선 간섭이 없어 결과가 같고, 유리해 보이도록 꾸미지 않고 동률로 표기했습니다. P3는 규정 속도라 속도로 만회할 여지가 없으므로 대피 후 자동 복구(R7)로만 처리합니다 — 화물 특성에 따라 회복 수단이 다르다는 것이 설계 포인트입니다.

**Q15. 시연의 due 값(P2=77초)은 어떻게 정했나?** *(v3.5 재도출 — 콘보이 OR2 집결로 파도가 빨라져 구 85초는 회복 없이도 정시가 되어 대조가 깨졌습니다)*
> 물리에서 역산했습니다. P2에게 처음부터 최고속을 강제해 측정한 도착 하한이 **75.10초**라 그보다 빠른 due는 달성 불가능한 목표이고, 회복을 끈 도착이 **79.27초**라 그보다 느린 due는 회복 없이도 정시가 되어 대조가 성립하지 않습니다. 즉 유효 구간은 75.1~79.3초이고, 양쪽에 회귀 오차(±0.2초) 여유를 두고 **77초**(+발령 1초 = 마감 78초)로 확정했습니다. 실측 결과는 회복 ON 76.60초(여유 1.40초) / OFF 79.27초(지각 1.27초), 회복 효과 2.67초입니다.
>
> 덧붙이면 due는 **EDD 정렬 키**이지 지킴을 보장하는 계약이 아닙니다 — P0의 시연 due 30초는 콘보이 4대의 물리 최단(약 67초)보다 짧아 애초에 도달 불가한 값이고, P0는 '즉시' 등급이라 마감 준수가 아니라 최단 도착이 목표입니다. 마감이 실제 제어에 개입하는 등급은 P2뿐입니다.

## 콘보이 집결·용량 개방 (v3.5 신규)

**★Q16. 블록 1대 원칙을 왜 콘보이만 깨나? 안전을 희생한 것 아닌가?**
> 깨는 게 아니라 **상한만 엽니다**. Code Crimson 활성 중, 그것도 **콘보이 캡슐에 한해** 블록 점유 상한을 1에서 4로 여는 것이고, 하위 등급과 평시 운행은 정적 용량 그대로입니다. 물리 안전은 그대로 유지됩니다 — **차두 규칙(선행 캡슐이 0.9m 전진해야 후속 진입)** 이 계속 작동하므로 짧은 블록(0.7m 등)은 애초에 한 대밖에 못 들어갑니다. 즉 용량이 아니라 **물리 간격이 수용량을 결정**하는 방식이고, 철도의 **이동 폐색(moving block)** 과 같은 원리입니다. 검증도 함께 했습니다 — R8 안전망 불변식 테스트가 개방 상태를 포함해 매 틱 30블록을 전수 검사하며 위반 0건이고, 모드 A·B에 공통 적용해(물리 운용 규칙이지 스케줄링이 아니므로) 비교 공정성도 유지했습니다.

**Q17. 콘보이 4대를 왜 OR1/OR2로 나누지 않고 OR2 한 곳에 모으나?**
> 대량수혈 프로토콜은 **한 수술방에서 동시에 여러 유닛을 쓰는** 상황이라, 혈액을 두 방에 나눠 보내면 정작 필요한 방에서 모자랍니다. 관제 관점에서도 목적지를 하나로 모으면 콘보이가 분기 없이 한 파도로 움직여 회랑 잠금 시간이 짧아집니다 — 실측으로 P0 개선폭이 −3.6%에서 **−5.8%로 확대**됐습니다. 비용은 도착부 직렬화입니다: OR2 지선에서 4대가 하역 2초씩 순차 도킹해 56.6 / 60.1 / 63.6 / 67.1초에 차례로 들어옵니다. 그래도 분산 배정보다 빠릅니다.

**Q18. OR1 경로는 왜 코드에 남겨 뒀나? 죽은 코드 아닌가?**
> **재해 시 분산 배정으로 복귀하는 옵션**입니다. 경로 테이블은 팀 ID 계약(동결 대상)이고, "어디로 보낼지"는 시나리오 정책입니다. 이 둘을 분리해 뒀기 때문에 OR2 집결은 `CONVOY_ROUTES` 한 줄로 바뀌고, OR1이 가용해지면 경로 자산을 그대로 다시 씁니다 — 정책 변경 때문에 계약(경로·ID)을 건드리지 않는 것이 설계 의도입니다. 현재 `P0_OR1` 은 어떤 캡슐에도 배정되지 않으며(명세 §4 각주), ST-OR1 자체는 P3 오염기구 회수의 출발지로 계속 쓰입니다.
